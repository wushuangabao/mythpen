## 风险分级

- **P1**：可能直接造成用户数据被静默覆盖、不可恢复丢失，或核心流程普遍不可用，需要优先阻断发布。

- **P3**：低频并发、可访问性、统计准确性或默认配置体验问题，不阻断核心数据安全，但仍应排期处理。

## P2

### P2-001 会话列表缺少激活代次，A→B→A 时旧响应可覆盖新状态

- **状态**：待解决
- **触发条件**：项目 A 的会话列表请求尚未完成时切到 B，再切回同一项目实例 A；旧 A 请求最后返回。相同项目内并发调用 `loadSessions` 也有同类问题。
- **影响**：旧会话列表可以覆盖新请求结果、改变当前选中会话并清空消息；两个空列表响应还可能各自触发默认会话创建，产生重复会话。
- **代码证据**：`src/stores/useAgentStore.ts:117-130` 只校验项目名和实例 ID，没有记录本次激活或加载请求的代次；回到同一 A 实例后旧请求仍会通过校验。`src/components/AIPanel.tsx:185-209` 在每次加载完成后独立判断空列表并创建会话，没有 single-flight 或幂等保护。
- **现有覆盖缺口**：`tests/agentProjectScope.test.ts` 覆盖了 A→B，但未覆盖 A→B→A 以及同一 scope 的乱序完成。
- **建议修复**：为项目激活增加单调递增 generation，并为 `loadSessions` 增加“仅最新请求可提交”的 ticket；默认会话创建应使用 single-flight 或服务端幂等键。
- **验收标准**：旧 A 响应在回到 A 后不能提交；任意乱序下最后一次加载结果胜出；多个空响应最多创建一个默认会话。

### P2-002 封面上传成功后刷新预览失败，会被误报为上传失败

- **状态**：待解决
- **触发条件**：`POST` 上传已经成功，但紧随其后的封面 `GET` 因瞬时网络、文件读取或缓存问题失败。
- **影响**：服务器上的封面已经更新，界面却提示“上传失败”并继续显示旧预览，导致用户重复操作；文件输入未重置时，重新选择同一个文件还可能不触发 `change`。
- **代码证据**：`src/pages/ExportPage.tsx:95-116` 将 `projectsApi.uploadCover` 和 `readProjectCover` 放在同一个 `try/catch`，任何后置读取错误都会落入上传失败分支。
- **建议修复**：分别处理“上传提交失败”和“预览刷新失败”；上传成功后先用本地文件生成乐观预览，后台单独重试服务器读取，并在流程结束时清空文件输入值。
- **验收标准**：上传成功、预览 GET 失败时仍明确显示“上传成功，预览刷新失败”；服务器与界面状态最终收敛；可连续选择同一文件重试。

### P2-003 章节版本冲突虽然已防止覆盖，但没有可完成的恢复流程

- **状态**：待解决
- **触发条件**：本地草稿保存期间，另一窗口或修订定稿先推进了章节 `data_version`，本次保存收到 `CHAPTER_VERSION_CONFLICT`。
- **影响**：权威正文不会被覆盖，这是已修复的安全边界；但草稿会一直保留旧 `baseDataVersion`，界面唯一操作是“重试”，因此每次重试都会继续冲突。若用户此时关闭应用，普通冲突草稿没有持久化保证，仍可能丢失。
- **代码证据**：`src/lib/editorSaveQueue.ts:125-150` 有意保留原始 `baseDataVersion`，`src/lib/editorSaveQueue.ts:193-206` 在失败后重新入队；`src/components/EditorContent.tsx:607-624` 对所有保存错误只提供通用重试。`src/lib/projectDraftRecovery.ts:118-143` 的持久化入口面向“项目实例退役”，不是活动实例内的普通 CAS 冲突。
- **建议修复**：识别 `CHAPTER_VERSION_CONFLICT` 并进入专用流程：加载权威正文、并排比较或合并、允许复制本地草稿、显式放弃，且只有在用户确认后才把草稿 rebase 到最新版本；冲突草稿应先持久化再提示。
- **验收标准**：冲突后用户可以安全完成“合并后保存 / 复制 / 放弃”之一；普通重试不会形成无效循环；重启应用后未处理草稿仍可恢复。

## P3

### P3-001 AI 续写基于旧上下文生成，却无条件追加到最新正文

- **状态**：待解决
- **触发条件**：续写生成过程中，另一窗口修改或定稿同一章节。
- **影响**：生成提示使用请求开始时的末尾上下文，保存时却重新读取最新正文并直接追加，可能产生语义断裂；保存还会把章节状态重置为 `writing`。现有逻辑通常不会覆盖已有正文，因此不列为 P1/P2。
- **代码证据**：`server/index.js:443-447` 读取请求开始时的章节内容构造提示；`server/ai-continue-save.js:42-58` 保存时重新读取当前内容、拼接续写，并无条件写入 `status = 'writing'`，没有校验起始 `data_version` 或内容哈希。
- **建议修复**：请求开始时捕获 `data_version`，保存时 CAS；发生冲突时拒绝直接追加，改为返回可审阅的候选续写或要求用户确认重基；状态更新也应基于原状态和版本条件。
- **验收标准**：生成期间章节被修改时不会自动追加；用户可审阅并决定如何合并；并发定稿不会被悄然改回 `writing`。

### P3-002 OpenAI-compatible 流在最终 usage 帧前中断时会漏记用量

- **状态**：待解决
- **触发条件**：OpenAI-compatible 流已经输出内容，但在提供最终 usage 帧之前断开、被取消或上游报错。
- **影响**：模型请求实际已经消耗 token，但 `token_usage` 可能完全不写入，导致统计偏低。该问题影响内部用量统计，不影响提供商实际计费和正文安全。
- **代码证据**：`server/ai-adapter.js:361-369` 仅在上游 payload 含 usage 时发出用量事件；`server/index.js:334-385` 与 `server/index.js:465-527` 的计数初始为 0，并在两项都为 0 时跳过记录。OpenAI-compatible 服务通常把 usage 放在流末尾，因此最终帧前中断时没有可写数据。
- **建议修复**：为不完整流记录 `usage_incomplete`；保留上游已报告的部分值，完全未报告时可记录可靠的本地估算并明确标记为估算，避免与精确计数混用。
- **验收标准**：内容已输出后中断会留下可识别的不完整用量记录；统计页面能区分精确值、部分值和估算值。

### P3-003 同一项目内章节被删除后，失败草稿可能成为不可见的内存孤儿

- **状态**：待解决
- **触发条件**：章节存在待保存或保存失败的正文草稿时，被另一窗口或 AI 工具删除；章节列表刷新后界面切到其他章节。
- **影响**：草稿仍留在进程级队列，但错误提示和草稿覆盖只绑定当前章节，用户无法再进入已删除章节进行复制或处置；若应用退出，该活动队列不会自动持久化。
- **代码证据**：`src/lib/editorSaveQueue.ts:19-27` 的活动草稿保存在内存 Map；`src/components/EditorContent.tsx:110-117` 只读取当前章节对应的草稿和错误；`src/lib/editorSaveQueue.ts:103-122` 仅在整个项目实例退役时把草稿隔离到持久化恢复区，没有处理“实例仍在、单章消失”的路径。
- **建议修复**：章节列表发现目标 ID 消失时，立即把对应正文和标题草稿隔离到持久化恢复区；恢复面板即使找不到目标章节，也必须允许查看、复制、导出和放弃。
- **验收标准**：带失败草稿的章节被删除后，草稿立即出现在恢复区；重启后仍可查看和复制；不会自动写入后来复用相同编号或 ID 的章节。

### P3-004 修订操作浮层未管理键盘焦点

- **状态**：待解决
- **触发条件**：键盘用户在修订块上按 Enter/Space 打开接受/拒绝浮层。
- **影响**：焦点仍停留在正文修订块；操作浮层位于所有修订块之后，前面还有多个块时需要经过大量 Tab 才能到达按钮，且关闭后没有明确的焦点恢复策略。
- **代码证据**：`src/components/RevisionReview.tsx:155-178` 将修订块渲染为按钮；`src/components/RevisionReview.tsx:181-206` 随后渲染 `role="toolbar"`，但没有 `ref.focus()`、Escape 处理或返回触发点的逻辑。
- **建议修复**：浮层打开时聚焦第一个操作按钮；支持 Escape 关闭；决定或关闭后把焦点恢复到原修订块或下一个待处理修订块。
- **验收标准**：纯键盘可以用一次激活进入操作按钮、用 Escape 返回，并连续处理所有修订块；焦点顺序可预测。

### P3-005 普通模型的长章节完整润色默认输出预算偏小

- **状态**：待解决
- **触发条件**：使用普通 OpenAI-compatible/Claude 模型对长章节执行“完整正文替换式”润色，且用户仍采用默认请求参数。
- **影响**：默认 4096 token 输出预算可能不足以返回完整长章，润色会频繁因输出上限被安全拒绝。当前完成性校验可防止截断正文落库，所以这是可用性和默认配置风险，不是数据安全风险。
- **代码证据**：`server/ai-request-parameters.js:11-18` 默认 `max_tokens` 为 4096；`server/ai-polish-request.js:29-47` 只为 Kimi K3 润色覆写到 `max_completion_tokens: 32768`，其他模型继续使用通用默认值。
- **建议修复**：为完整章节润色提供独立、可按章节长度估算的输出预算，并受模型上限约束；无法满足最低预算时在请求前给出明确提示，而不是等待生成后失败。
- **验收标准**：长章请求会选择足够且合法的模型预算；预算不足可在请求前预警；截断结果仍不得创建修订。
